- 日期：2026-10-07

## 排序原则

按「**是否服务『AI 接上体系』主线**」×「**不做会不会出问题**」双轴排序，而非按缺陷级别机械排序。
评价列是我的判断，不是待议选项。

| 梯队 | 方向 | 一句话理由 |
|---|---|---|
| T1 | AI 能力层 | 直接兑现「让 AI 接上体系」的战略目标 |
| T2 | 安全与可观测 | 现在没出事是因为还没上线，不是因为安全 |
| T3 | 数据一致性 | 会产生错误数据，但用户暂时看不见 |
| T4 | 整洁度 | 不修不影响运行，但每次进项目都要踩一遍 |

## T1 — AI 能力层（建议优先）

### 1. MCP Server 暴露：让 AI 真的能调用，而不只是读到

有了 `openapi.json` 之后，把它转成 MCP tools 是很自然的一步 —— 这才能把「给 AI 看的文档」变成「AI 可直接操作的工具」。

| 项 | 说明 |
|---|---|
| 依赖 | 必须先完成接口元数据 S1–S3（产出稳定的 `openapi.json`） |
| 形态 | 独立小服务或本项目的 `--mcp` 启动模式；每个 endpoint 映射为一个 tool，`summary`→工具描述，`ai_hint`→使用说明，`requestSchema`→入参定义 |
| 鉴权 | tool 调用需携带用户 JWT，权限仍走现有 `RequirePerm`（**不要给 AI 开后门**） |
| 工作量 | 中（约 300–400 行 + 转换层） |
| 评价 | ⭐ **最高价值项**。你的目标既然是「AI 直接接上体系」，只读文档只能让 AI 写代码去调，有了 MCP 是 AI 自己就是调用方 |

### 2. 前端 TS 类型自动生成（消灭前后端类型漂移）

`openapi-typescript` 依据 `openapi.json` 生成 `frontend/src/api/types.ts`，替代手写的那份。

| 项 | 说明 |
|---|---|
| 直接收益 | 修复 **P3-15**（前端虚标 `UserInfoResponse.orgName`、`AppVO.ownerId`/`updatedAt`，后端实际不返回）；防止今日 **P1-1 / P1-2** 这类契约漂移再次发生 |
| 附带收益 | 今日改的 `BindCodeVO.qrContent/expireAt`、`AppListKeys` 的 `PageResponse`，前端类型会同步更新，不必再人工核对 |
| 工作量 | 小（一个 npm script + CI 步骤） |
| 评价 | ⭐ **性价比最高**。投入极小，且把「前后端契约」从人工维护变成机器保证 |

### 3. 导出 OpenAPI → 文档站 / Mock Server

一份 Schema 产出三样东西：`docs/ 静态文档`（顺带解决 **P3-10** 文档缺失）、
`prism/msw` mock（前端可脱离后端开发）、Postman/Apifox 导入（联调不再口口相传）。

| 评价 | ⭐ 建议做，成本几乎为零（S3 的副产品） |
|---|---|

### 4. 权限 ↔ 接口的反查治理

元数据齐了之后，可以做两个现在做不到的查询：

- 「某角色实际能访问哪些接口」—— 遍历该角色的菜单权限码 → 反查所有端点，一键看清权限边界
- 「哪些端点没有任何角色能触达」—— 僵尸接口检测（当前 `tenants` 的 4 个端点就是这种形态）

| 评价 | ⭐ 对 RBAC 系统是刚需，且实现只是几条 SQL |
|---|---|

## T2 — 安全与可观测（上线前必须做）

### 5. token 版本化 + 登出真正生效（P2-7）

**现状**：改密码后旧 access token 仍有效 60 分钟；`/api/auth/logout` 是空操作返回 OK。

这不是"待优化"，是"改了密码跟没改一样"。

| 项 | 说明 |
|---|---|
| 方案 | `sys_user` 加 `token_version INT`；JWT 携带 `ver` claim；`AuthMiddleware` 校验一致性；改密/踢出时自增 |
| 附带 | 前端存了 `refreshToken` 却从未使用（401 直接踢登录），`/api/auth/refresh` 实为死接口 —— 要么实现静默刷新，要么删掉，别留半截 |
| 评价 | 🔴 **上线前必做** |

### 6. 登录失败限流（P2-8）

**现状**：无失败计数、无验证码、无 IP 限流 → 可直接暴力破解。

| 方案 | 用户维度失败计数 + 指数退避；SQLite 下用表或内存计数均可（单机够用） |
|---|---|
| 评价 | 🔴 **上线前必做**，实现约 50 行 |

### 7. 访问日志 + 审计日志（P2-3）

**现状**：只有 `gin.Recovery()`，未挂 `gin.Logger()`，生产无法排障。

| 项 | 说明 |
|---|---|
| 访问日志 | `gin.LoggerWithWriter` 落文件，短期收益立竿见影 |
| 审计日志 | **更重要**：记录「谁在何时调了哪个接口、改了什么」，AI 接入后尤其需要知道 AI 干了什么。接口元数据表正好提供 `endpoint_key` 作为审计记录的关联键 |
| 评价 | 🔴 访问日志必做；审计日志在 AI 接入（T1-1）前必须就位 |

### 8. JWT 算法显式校验（P2-6）

`keyfunc` 未断言 `t.Method`。`jwt/v5` 默认拒绝 `none`，风险有限，但显式判断只要 3 行。

| 评价 | 🟡 顺手做，成本极低 |
|---|---|

### T4 里我最想让你立刻做的是 18

其余的品质问题影响的是"看着不爽"，但 **`product.ts` 这个死接口文件会直接误导 AI** ——
你正准备把这套契约喂给 AI，一个不存在的 `/api/products` 会被 AI 当成真实能力去调用。
这与本阶段目标直接冲突，建议先清掉。

## 关于 P3-12 的单独说明

> `PUT` 复用 `Create` 结构体，`binding:"required"` 导致更新时必须回传 `name`/`code`

这条在实现「接口元数据」时会自然暴露出来：`UpdateAppRequest` 与 `CreateAppRequest` 若共用结构体，
导出的 Schema 会让 AI 以为更新也要必填 `name`/`code`，从而生成错误的调用。

**建议在元数据 S2 阶段顺带拆分 Update 专用结构体**，否则 `required` 字段会污染给 AI 的契约。
这不是洁癖，是直接影响 AI 调用正确率。
