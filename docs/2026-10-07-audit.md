## P0 致命

### P0-1 `UserUpdate` 接受 `password` 字段 —— 绕过「重置密码」权限，接管任意账号

- 定位：`backend/service.go:205-213`（`UpdateUserRequest.Password`）、`backend/service.go:640-646`（`UserUpdate` 分支处理）
- 路由：`backend/handler.go:130` `users.PUT("/:id", RequirePerm("system:user:edit"))`
- 影响：只需 `system:user:edit` 权限，即可 `PUT /api/users/1 {"password":"x"}` 直接改写 `admin` 的密码完成接管。`system:user:reset-pwd` 权限、前端「重置密码」按钮的 UI 隐藏**全部被绕过**。
- 补充：前端 `src/api/user.ts` 的 `UpdateUserRequest` 注释写着「后端不支持改 username / password」—— **前端认知与后端实现不符**，说明该字段是后端单方面残留。
- 修复：删除 `UpdateUserRequest.Password` 及 `UserUpdate` 内的密码分支（改密只走 `PUT /:id/password` + `RequirePerm("system:user:reset-pwd")`）。

### P0-2 `UserAssignRoles` 不限制可授予的角色 —— 自我提权

- 定位：`backend/service.go:669-676`（`UserAssignRoles`）、`backend/service.go:712-719`（`assignRolesInternal`）
- 路由：`backend/handler.go:151` `RequirePerm("system:user:assign-role")`
- 攻击链（当前即可复现）：以 `user_admin` 登录（seed 已授予 `system:user:assign-role`）→ `PUT /api/users/{自己的id}/roles {"roleIds":[<super_admin 的 id>]}` → `AuthMiddleware` 下一请求即判 `isSuper=true`，全权限短路放行。
- 关联缺陷：`RoleCreate`（`service.go:797`）同样不禁止创建 `code = "super_admin"` 的角色。当前被 `code` 唯一索引偶然挡住（种子已占用该 code），属**纵深防御缺失**而非可用路径。
- 修复：
  1. `assignRolesInternal` 前校验：非超管调用者不得授予含 `super_admin` 的角色；
  2. 校验 `roleIds` 存在且 `status=1`（当前可写入指向不存在角色的孤儿记录）；
  3. `RoleCreate` 显式拒绝 `code == RoleSuperAdmin`。

### P0-3 数据权限只覆盖列表查询 —— 单实体接口全部越权（IDOR）

- 已实现数据权限的**唯一**位置：`UserPage`（`service.go:501-519`）
- 完全缺失数据权限校验的接口：

| 路由 | 处理函数 | 定位 |
|---|---|---|
| `GET /api/users/:id` | `UserGetVO` | `service.go:571` |
| `PUT /api/users/:id` | `UserUpdate` | `service.go:617` |
| `DELETE /api/users/:id` | `UserDelete` | `service.go:651` |
| `PUT /api/users/:id/roles` | `UserAssignRoles` | `service.go:669` |
| `PUT /api/users/:id/posts` | `UserAssignPosts` | `service.go:678` |
| `PUT /api/users/:id/password` | `UserResetPassword` | `service.go:687` |
| `GET /api/users/:id/roles` \| `/posts` | `UserRoleIDs` / `UserPostIDs` | `service.go:700,706` |

- 影响：`DEPT_ONLY` / `DEPT_AND_BELOW` / `SELF_ONLY` 角色的用户，只要持有对应动作权限，就能读取并改写**任意组织**的用户（含重置其密码）。列表分页限制形同虚设——换个 `id` 即可。
- 修复：抽出 `assertUserInScope(callerUID, targetUID) *AppError`，在全部单实体入口前置调用；`DELETE` 另需补「不得删除超管账号」的判断（当前只挡了 `username == "admin"` 字面量，改名后即失效）。

### P0-4 开放接口签名不覆盖 query / body，且 nonce 不落库

- 定位：`backend/middleware.go:184-190`
  ```go
  payload := strings.Join([]string{apiKey, ts, nonce, c.Request.Method, c.Request.URL.Path}, "\n")
  ```
- 缺陷 1：`URL.Path` 不含 query string。`GET /api/open/userinfo?appUserId=X` 的签名，改成 `?appUserId=Y` **依然验签通过** → query 可任意篡改。
- 缺陷 2：body 完全不在签名内，`POST /api/open/bind/apply` 的请求体可被替换。
- 缺陷 3：`X-Nonce` 仅参与签名、未落库去重，配合 300s 时间窗（`appSignatureSkewSeconds`，`middleware.go:119`）**同一请求可在 5 分钟内无限重放**。
- 修复：
  1. payload 追加 `RawQuery` 与 body 的 SHA-256；
  2. nonce 写入带 TTL 的去重表（或复用 SQLite 建 `open_nonce` 表 + 定期清理），重复即拒；
  3. `appSignatureSkewSeconds` 提到 `Config`（当前硬编码）。
- 另：`middleware.go:194` 每个开放接口请求都同步 `UPDATE last_used_at`，在 SQLite 单写者模型下会放大写锁竞争，建议降频或异步。

## P1 高

### P1-1 密钥列表接口返回裸数组，前端按 `res.list` 取值 → 密钥列表恒为空

- 后端：`handler.go:468` → `svc.AppListKeys` 返回 `[]AppKeyVO`，`OK(c, resp)` 直接输出**裸数组**
- 前端：`src/views/system/app/index.vue:274-275`
  ```ts
  const res = await appApi.pageAppKeys(currentApp.value.id, { page: 1, pageSize: 100 });
  keys.value = res.list;   // ← undefined
  ```
- 同时 `src/api/app.ts` 声明返回 `Promise<PageResponse<AppKeyVO>>`，且向接口传了后端不读的 `page/pageSize`
- 影响：**「密钥管理」弹窗永远显示空白列表**，用户以为密钥丢失（实际仅在创建响应里出现过一次 `apiSecret`，更易误判）
- 修复：二选一 —— 前端改为 `Promise<AppKeyVO[]>` 并直接赋值；或后端统一改为 `PageResponse`。**推荐改前端**，与 `posts` / `bind` / `roles/{id}/menus` 的裸数组约定保持一致。

- 前端确实会提交 `status: 0`（`src/views/system/user/index.vue:249,259`、`role/index.vue:232`）
- 后端却用 `!= 0` 做守卫：

| 位置 | 代码 | 被吞掉的合法值 |
|---|---|---|
| `service.go:637-639` | `if req.Status != 0 { u.Status = req.Status }` | **status=0（禁用用户）** |
| `service.go:834-836` | `if req.Status != 0 { r.Status = req.Status }` | **status=0（禁用角色）** |
| `service.go:963-965` | `if req.SortOrder != 0 { m.SortOrder = req.SortOrder }` | sortOrder=0 |
| `service.go:1131-1133` | `if req.ParentID != nil { o.ParentID = req.ParentID }`（OK）但没有 `parentId → null` 通路 | 无法置空 |
| `service.go:634-636` | `if req.OrgID != nil { u.OrgID = req.OrgID }` | 无法清空 orgId |
| `service.go:831-833` / `1221-1223` / `1285-1287` | `SortOrder` / `TenantID` / `Status` 同类 | 同上 |

- 影响：**管理员在 UI 上把用户/角色切到「禁用」，保存后仍是「启用」**，无任何报错（静默失败）

### P1-4 `CORS_ORIGINS` 配置项完全失效，且硬编码了非法组合

- 定位：`backend/config.go:28,49` 定义并读取 → **全项目零引用**
- `backend/middleware.go:19-32` 硬编码：
  ```go
  c.Header("Access-Control-Allow-Origin", "*")
  c.Header("Access-Control-Allow-Credentials", "true")   // 与 * 组合被 CORS 规范禁止
  ```
- 影响：`.env.example` 里「生产请改为具体前端 origin（逗号分隔）」的说明**是假的**，改了不生效。当前能用只是因为 axios 未开 `withCredentials`；一旦启用 cookie/凭证模式立即全站跨域失败
- 修复：`CORSMiddleware(origins []string)`，从 `cfg.CorsOrigins` 解析白名单，命中则回显具体 origin + 只对白名单设 `Allow-Credentials`；`*` 时不得设 credentials。

### P1-5 `busy_timeout` 只作用于连接池首个连接 → 并发写仍报 `database is locked`

- 定位：`backend/main.go:33-42`
  ```go
  db.Exec("PRAGMA journal_mode = WAL;")
  db.Exec("PRAGMA busy_timeout = " + itoa(...))   // ← 只命中池中一个连接
  sqlDB.SetMaxOpenConns(cfg.DBMaxOpenConns)        // 允许最多 4 条连接
  ```
- 原理：`journal_mode` 是持久化在库文件头的（生效）；`busy_timeout` 是**每连接**的会话变量，后续新建的连接**不继承**。DSN 是纯路径（`sqlite.Open(cfg.DBPath)`），未带 pragma → 新连接 `busy_timeout = 0`，写冲突立即 `SQLITE_BUSY`，`DB_BUSY_TIMEOUT_MS=5000` 形同虚设
- 修复：把 pragma 写进 DSN（`glebarez/sqlite` 基于 modernc，支持 `_pragma=`）：
  ```go
  dsn := fmt.Sprintf("file:%s?_pragma=busy_timeout(%d)&_pragma=journal_mode(WAL)&_pragma=foreign_keys(1)",
      cfg.DBPath, cfg.DBBusyTimeoutMs)
  ```
  退化方案：`SetMaxOpenConns(1)` 强制单连接（牺牲并发读，最保守）。

### P1-6 组织树 / 菜单树无环检测 → 可造成节点静默消失

- 定位：`OrgUpdate`（`service.go:1126-1156`）可直接接受任意 `parentId`，**不校验是否为自己或自己的子孙**
- 后果推演：`A.parent = B` 且 `B.parent = A` → `OrgTree`（`service.go:1057-1092`）建索引时两者都不在 `roots` 中（互为父节点）→ **两个组织在树里彻底消失**，且不报错
- 菜单侧：`assertMenuIntegrity`（`service.go:1030-1053`）只查了「自己作自己的父节点」和「孤儿节点」，**没有查环**，同样可静默丢失
- 附带：`ResolveDataScope` 的 `order` map 缺 key 时按「最窄」兜底（`repo.go:54-66`），所幸失败安全，但 `RoleCreate`/`RoleUpdate` 不校验 `dataScope` 枚举，会写入非法值
- 修复：`OrgUpdate` / `MenuUpdate` 增加「新 parentId 不得等于自身、不得位于自身子孙集合内」校验（可复用 `DescendantOrgIDs`）。同时给 `dataScope` 加白名单校验。

> 把 **query string** 与 **请求体 SHA-256 十六进制串**一并加入待签串，否则全部 `/api/open/**` 请求将验签失败。
> 待签串顺序：`apiKey \n ts \n nonce \n METHOD \n path \n rawQuery \n sha256(body)`。
